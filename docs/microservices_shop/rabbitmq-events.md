# События RabbitMQ в Microservices Shop

Через RabbitMQ Payment Service сообщает Order Service об успешном завершении имитации оплаты. HTTP-вызов Order Service запускает платёж, а сообщение RabbitMQ запускает обновление статуса заказа.

## Маршрут события завершения оплаты

- Издатель — Payment Service. Он создаёт exchange при старте приложения и публикует событие после сохранения платежа со статусом `completed`.
- Получатель — Order Service. При старте он объявляет exchange и очередь, привязывает очередь с ключом маршрутизации события завершения оплаты и регистрирует обработчик.
- Тело сообщения — объект JSON, передаваемый в виде байтов UTF-8. В теле нет отдельных полей для имени или версии события.

## Поля сообщения об успешной оплате

| Поле | Тип и смысл |
|---|---|
| `event_id` | UUID в виде строки, идентификатор события. |
| `created_at` | Строка ISO 8601 с временем формирования события в UTC. |
| `payment_id` | Строковый идентификатор завершённого платежа. |
| `order_id` | Строковый идентификатор заказа, к которому относится платёж. |
| `amount` | Числовая сумма платежа. |
| `status` | Строка `completed`. |

Пример показывает событие с условными идентификаторами и суммой 2800.

```json
{
  "event_id": "19da1232-b694-4c81-a8c5-ba5f9daf2048",
  "created_at": "2026-01-01T12:00:00+00:00",
  "payment_id": "payment-demo-1",
  "order_id": "order-demo-1",
  "amount": 2800.0,
  "status": "completed"
}
```

## Как Order Service применяет событие

Order Service декодирует тело сообщения и открывает отдельную сессию БД. Он находит заказ по `order_id` и сохраняет статус `paid`. Если заказ отсутствует, в сообщении нет `order_id` или заказ уже оплачен, обработчик завершает работу без изменения записи.

Обработчик полагается на маршрутизацию события и использует из тела `order_id`. Поля `amount`, `status` и `payment_id` отдельно не проверяются. Повторное сообщение для заказа, который уже имеет статус `paid`, пропускается. Таблица обработанных `event_id` отсутствует.

## Сохранение, подтверждение и сбои

Обработка выполняется внутри `message.process()`. Когда обработчик меняет статус заказа, он дожидается фиксации изменения в БД перед выходом из контекста обработки. Ошибка декодирования или сохранения логируется и пробрасывается. Специальная политика повторов и очередь для необработанных сообщений в коде не настроены.

Payment Service сначала фиксирует `completed` в БД, затем публикует сообщение. При сбое между этими операциями платёж может иметь статус `completed`, а заказ остаться в `created`. Автоматическая повторная публикация из БД через outbox не реализована.

## Что будет, если сервис заказов упадёт после оплаты

Состояние заказа зависит от того, успел ли Order Service
зафиксировать статус `paid` в БД до сбоя.

- Сбой до фиксации `paid`. Заказ остаётся в `created`.
  После восстановления он перейдёт в `paid`, если событие
  об оплате будет успешно доставлено и обработано.
- Сбой после фиксации `paid`. Заказ сохраняет статус `paid`.
  Повторное событие будет пропущено обработчиком.

Если Payment Service уже зафиксировал платёж как `completed`,
падение Order Service не меняет этот статус.

Сохранение платежа и публикация события выполняются отдельно.
При сбое публикации возможна ситуация, когда платёж имеет
статус `completed`, а заказ остаётся в `created`.
