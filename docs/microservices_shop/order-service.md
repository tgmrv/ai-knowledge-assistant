# Order Service

Order Service создаёт и хранит заказы, рассчитывает их стоимость по данным Catalog Service и обрабатывает событие об успешной оплате. Order Service хранит заказ отдельно от записи платежа в Payment Service.

## Маршруты заказов

| Внутренний путь Order Service | Внешний путь через gateway | Результат |
|---|---|---|
| `POST /orders` | `POST /api/orders` | Создаёт заказ, вызывает Payment Service и возвращает заказ. Успешный статус внутри сервиса — `200`, через gateway — `201`. |
| `GET /orders/{order_id}` | `GET /api/orders/{order_id}` | Возвращает заказ или `404`. Gateway проверяет владельца. |
| `GET /orders` | — | Возвращает список всех заказов через внутренний API. |

## Контракт создания заказа

Тело содержит строковый `user_id` и список `items`. У каждой позиции есть строковый `product_id` и целочисленный `quantity`. При внешнем вызове gateway требует Bearer-токен и заменяет `user_id` идентификатором из JWT. В примере используются условные идентификаторы.

```json
{
  "user_id": "user-demo-1",
  "items": [
    {"product_id": "product-demo-1", "quantity": 2}
  ]
}
```

В ответе возвращаются `id`, `user_id`, `status`, `total_price` и `items`. Каждая позиция ответа содержит `product_id`, `product_name`, `quantity` и `item_price`. `created_at` хранится в таблице `orders`. Текущая схема ответа заказа его не включает.

## Как Order Service сохраняет заказ

1. По каждому `product_id` сервис запрашивает товар у Catalog Service.
2. Сервис сохраняет название и цену товара в позиции заказа. Стоимость заказа — сумма `item_price × quantity` по всем позициям.
3. Заказ со статусом `created` и его позиции сохраняются в `orders` и `order_items` одной транзакцией.
4. После фиксации заказа сервис вызывает внутренний `POST /payments` с `order_id` и суммой. Order Service ждёт HTTP-ответ Payment Service. Статус `paid` выставляет обработчик RabbitMQ.

## Статусы заказа и чтение после оплаты

| Статус заказа | Когда устанавливается |
|---|---|
| `created` | При сохранении нового заказа перед обращением к Payment Service. |
| `paid` | Когда Order Service обработал сообщение об успешной оплате и сохранил изменение. |

Сессия создания заказа обновляет объект из БД до вызова Payment Service. После вызова сервис возвращает этот объект, поэтому клиент может получить `created`. Для чтения актуального статуса используется `GET /api/orders/{order_id}`.

Если вызов Payment Service завершается исключением, заказ уже сохранён. Ответ создания может быть ошибкой, а состояние заказа зависит от того, успело ли событие оплаты дойти до обработчика. У повторного `POST /api/orders` нет ключа идемпотентности, поэтому повтор может создать новый заказ.
